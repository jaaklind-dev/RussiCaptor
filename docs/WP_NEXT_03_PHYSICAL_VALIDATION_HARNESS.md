# WP-NEXT-03 physical validation harness

The normal CM workspace deliberately prevents a non-owner from editing a patient. That is the intended operational safeguard, but it makes three server-side race cases impossible to demonstrate through ordinary two-CM taps alone.

The `SharedWorkflowValidationCard` is compiled only when a signed `upgrade-validation` or `rollback-validation` artifact is built with `RUSSICAPTOR_ENABLE_SHARED_WORKFLOW_VALIDATION_HARNESS=1`. The canonical field-release build rejects that variable and has no card.

The card is not a mock backend. It issues normal authenticated client requests through `apply_shared_workflow_patient_mutation`, retaining command IDs, authenticated actor attribution, ownership checks, idempotency and server CAS. It supports:

- simultaneous physical-client `CLAIM` requests;
- a prepared former-owner proposal submitted after a normal transfer, which must be rejected by ownership/CAS;
- two distinct `APPEND` commands prepared from one captured authoritative revision, with separate explicit submission controls;
- two same-base `MUTABLE` proposals from two physical sessions of the same current CM identity. This isolates CAS stale-version behavior without weakening the distinct-CM ownership rule.

Preparation now constructs a private cloned proposal without modifying repositories, notifying sync or submitting a request. No local mutation/rollback is needed. The test marker is a validation-only note payload; it has no clinical effect. A fixture used for this harness is technical evidence only and must not be treated as a clinical exercise record.

## Hardened context and command safety (2026-10-19)

The operator explicitly confirms the exact `EX-*` TEST exercise and chooses a non-secret client reference (`Samsung-A` or `Samsung-B`). Arming requires the validation build gate, RUNNING/current exercise identity, online hydrated workflow, the exact composed `russicaptor.runtime-continuity-reference@1.0.0` package/hash, verified fresh Auth/profile, and an active exercise-scoped CM assignment. EXCON authority for this exercise and active GLOBAL assignments are rejected. This does not grant an entitlement or bypass server checks.

There is **no authoritative server TEST boolean** in the current runtime snapshot. The restriction therefore combines the closed technical package with explicit operator TEST acknowledgement and independently audited exercise selection. It must not be described as a server-enforced TEST lifecycle flag. Creating the one future TEST exercise still requires separate authorization, including acceptance of a possible inactive READY residue; READY cancellation remains OFF.

Each frozen prepared descriptor binds exercise, patient, operator, non-secret Auth session generation, arming context, command kind, base revision and command ID. The actual cloned proposal remains in a bounded in-memory registry (16 commands). Copies/forged descriptors are not accepted. Exercise, package, lifecycle or Auth context invalidation clears the registry; leaving and returning cannot resurrect it. Unmount/restart discards preparations. Disconnect alone retains a preparation but blocks sending until online. No authentication material is persisted or transferred.

Immediately after the asynchronous Auth lookup, and again before each RPC invocation, the real authenticated operator, selected technical patient and captured context must still match. A late response cannot restore data or shared-workflow heads into a replacement context. Ownership changes and newer patient revisions never rewrite a staged proposal. The normal route is disabled for changed ownership or a stale MUTABLE/CLAIM base; the separate confirmed negative route below is required for a known-stale server rejection.

The APPEND-pair control captures one verified head and one state snapshot, then creates two stable distinct command IDs. Both descriptors visibly show the same base revision. Neither is sent until its individual send control is activated. APPEND freshness follows the existing append-only contract: the current head may advance but must never regress below the captured base, and ownership must still match. Requiring revision equality would incorrectly prohibit the second same-base append. CLAIM instead requires an unowned patient and exact revision; MUTABLE requires current self-ownership and exact revision. Preparation requires a verified head of revision at least one. There is no selectable patient route in this card: it is explicitly bound to `PT-PELVIC-001`; a changed patient context is rejected.

Every prepared command is one-shot in either route. Pending, completed or previously submitted controls are disabled. Direct duplicate invocation shares the in-flight result or returns its cached outcome without another request. Lost/unknown responses consume the preparation: preserve evidence and inspect the server ledger; do not create a replacement command or manually resend. Only the normal production gateway's existing single ambiguous-response retry remains unchanged. The server ledger remains the authority for materialization. No revision editing, service-role client, ownership bypass or alternate RPC exists.

### Confirmed negative TEST submission policy

The user-authorized negative route is restricted to a registered, immutable, never-submitted MUTABLE command whose authoritative head is already **strictly newer** than the captured base. That monotonic mismatch guarantees rejection by the unchanged server CAS contract even if ownership later returns to the original CM. APPEND and CLAIM cannot use this route. No manual base edit, arbitrary command construction or stale-credential replay is offered. Absence/change of ownership may be tested only together with the proven stale base; it is not permission to mutate an unowned patient.

The operator must confirm a separately labelled negative TEST dialog. Cancel submits nothing. Context, patient activity, lifecycle, Auth, scope, head mismatch and one-shot state are checked again on confirmation and after Auth lookup. SDK retries are explicitly disabled per request with `retry(false)` and the gateway's ambiguous-response retry is disabled only for this negative request. Canonical requests retain their retry policy. No negative response, including an unexpected APPLIED, is materialized locally or added to local workflow heads.

Only actual STALE_VERSION, NOT_OWNER or OWNERSHIP_CHANGED is accepted as ownership/CAS rejection evidence. Transport ambiguity, authorization failure, IDEMPOTENT, APPLIED or any other unexpected response is preserved and latches STOP for this harness process; re-arming cannot clear it. Export the evidence and inspect authoritative server state through supported read-only operations. An unexpected APPLIED is a potential server contract violation, never a claimed successful negative test; do not compensate by direct mutation. This guard cannot promise to undo a broken backend. The no-mutation guarantee depends on the unchanged monotonic CAS contract, verified by regression tests. Ownership/CAS outcomes must never be relabelled WRITER_GENERATION_STALE.

## Bounded evidence and limitations

The card exposes and explicitly shares only the last 64 metadata events: client reference, exact exercise/patient/command/context reference, shortened operator reference, command kind, captured base revision, client submission/response UTC timestamp, phase/attempt, HTTP response status when available, structured SQL/PGRST error code, actual returned status/revision and shortened owner reference. It excludes full patient state, notes, raw errors, passwords and Auth material.

`SUBMITTED` means the SDK RPC invocation was initiated, not proof of server receipt. `RESPONSE` requires an actual HTTP status (100–599). Fetch failures/status zero and thrown transport failures are `TRANSPORT_UNKNOWN`, with null HTTP status. `LOCAL` is a pre-send rejection. `requestCorrelationId` is always null because the supported SDK response does not expose server request headers; command ID is the ledger/audit correlation, not an invented server request ID. Client timestamps are not server timestamps. The observer describes gateway SDK invocations, not any internal SDK transport retry. Normal release/transfer controls continue using their existing authoritative path; read their outcomes/ledger separately rather than attributing fabricated observer events to them.

Evidence export is explicit and must be saved to the controlled acceptance archive **before** disarming, switching modes or resetting context. The harness is not a durable audit store. Server read-only command-ledger/head and ownership readback must corroborate IDs, revisions, one materialization per command and owner outcomes. Server rejection priority may return STALE_VERSION before NOT_OWNER/OWNERSHIP_CHANGED; record the actual code rather than requiring an invented one.
