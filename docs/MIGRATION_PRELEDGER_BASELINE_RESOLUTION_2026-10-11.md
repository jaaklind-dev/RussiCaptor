## Supabase tooling and candidate strategies

Current [Supabase migration-list documentation](https://supabase.com/docs/reference/cli/supabase-migration-list) says local files and remote history are compared by **version/timestamp**, not semantic name. [Migration repair](https://supabase.com/docs/reference/cli/supabase-migration-repair) with `--status applied` **inserts a history record without executing SQL**; `--status reverted` removes a history record, not schema objects. [Database push](https://supabase.com/docs/reference/cli/supabase-db-push) applies missing migrations and has `--dry-run`; `--include-all` explicitly includes all versions absent from remote history. [Local reset](https://supabase.com/docs/reference/cli/supabase-db-push) replays all files in `supabase/migrations`. Those documented rules, plus a deterministic comparison of the 50 local filenames and 42 live versions, are the simulation for this read-only WP. No live `db push` or live repair was invoked.

## Fresh database reproducibility is a separate contract

Keep all eight original files in `supabase/migrations` so a fresh database can replay them in source order. This is a documented, versioned two-stage bootstrap path, not a claim that its automated replay has passed. A later dedicated WP should test it and, if desired, codify the shared-state precursor as a first migration with a separate production-history treatment; that is outside this no-SQL-change WP. On production, its ledger marker stays empty and its later successor's resulting behavior is already live. This asymmetry is explicit; a scratch replay/schema comparison is required before calling fresh-environment equivalence fully *tested*.
