## Product vision

RussiCaptor is a mobile Case Manager platform for mass-casualty and disaster
medicine exercises. It is intended to support both participants and exercise
control (EXCON).

The current demonstration scenario is a botulism exercise. The first complete
workflow is centered around one Case Manager and one patient, but the design
must support multiple patients, users, and devices later.

The intended participant workflow is:

1. A Case Manager signs in.
2. The Case Manager scans a patient's QR code or enters the national ID.
3. The patient is assigned to the Case Manager.
4. The Case Manager works in the patient workspace: overview, timeline, labs,
   imaging, questions, orders, and notes.
5. Data and scenario events are revealed according to user actions and the
   exercise clock.

The intended EXCON workflow is:

1. Start, pause, or stop an exercise session.
2. Change exercise speed or advance the exercise clock manually.
3. View upcoming scenario events and adjust their trigger times.
4. Observe participant actions and reveal or trigger scenario information.

## Architecture decisions

The UI must not depend directly on the final data source. The intended layering
is:

```text
UI -> repositories/services -> providers -> data source
```

The current data source is in-memory demo data. The planned production source
is an exercise-specific Excel workbook stored in OneDrive or SharePoint and
accessed through Microsoft Graph.

One workbook represents one exercise. The current proposed sheets are:

- Patients
- Questions
- Labs
- Imaging
- Notes
- Orders

Timeline entries are generated by the application and are not authored in the
Excel workbook. See `docs/EXCEL_SCHEMA.md` for the current column proposal.

Core records such as questions, lab results, imaging studies, orders, and
timeline events remain independent objects linked by `exerciseId` and
`patientId`. They must not be nested inside `Patient`.

Important architectural limitation: provider abstraction currently covers only
patients. The other repositories still import demo arrays directly. Before the
OneDrive implementation, either extend `DataProvider` across all domains or
introduce focused provider interfaces for each repository.

## React state decision from earlier development

The EXCON screen owns a copied `ExerciseSession` state and passes it to cards as
props. In particular, `UpcomingEventsCard` must derive the current minute from
its `session` prop instead of reading `getExerciseSession()` independently.
This ensures React re-renders remaining time, event state, and next-event
highlighting whenever the clock updates.

Use the same principle for future EXCON cards: keep one authoritative screen
state and pass required values to child components. Repository objects may
remain mutable during the demo phase, but React components still need a clear
state or subscription boundary to trigger rendering.

## Order-to-result workflow completed on 2026-07-20

The first end-to-end EXCON scenario workflow is implemented locally:

- Demo orders define their result action, target, delay, title, and description.
- Placing an order moves it to `processing` and schedules a scenario event at
  the current exercise minute plus the configured delay.
- EXCON displays the generated event and allows its trigger time to be adjusted.
- Reaching the trigger minute makes the lab panel or imaging study available,
  completes the originating order, and creates one result timeline entry.
- Unsupported scenario actions remain pending instead of being marked executed.

The Android verification used the CT head order and confirmed the visible flow:

```text
Tellimata -> Täitmisel -> EXCON: 3 min pärast -> Valmis
```

The patient timeline contained exactly `KT pea tellitud`, `KT pea täitmisel`,
and `KT pea valmis`.

Recommended continuation: add automated service-level tests and define reset
semantics for stopping or restarting an exercise before expanding the remaining
scenario actions.

## Exercise reset and automated tests completed on 2026-07-20

The EXCON controls now have explicit lifecycle semantics:

- `Pause` preserves the exercise minute, speed, assignments, clinical state,
  timeline, orders, and pending events.
- `Stop` stops the clock and restores the complete demo exercise baseline:
  minute zero, speed ×1, no assignments, no timeline or pending events, hidden
  questions, unplaced orders, and unreleased lab/imaging results.

Jest is configured through the Expo-recommended `jest-expo` preset. Service
tests cover the order-to-result workflow, full Stop reset, and Pause state
preservation. Run them with `npm test`.

## Patient completion added on 2026-07-20

EXCON has a patient-specific `Finish` action for assigned active patients.
Finishing a patient sets the status to `Completed`, removes the patient from the
Case Manager's active list, cancels that patient's pending scenario events, and
adds an EXCON status entry to the timeline. Clinical data and existing history
remain unchanged. This is separate from exercise `Stop`, which still restores
the complete demo baseline, including patient statuses.

Completed patients are listed under `History`. Opening one shows the preserved
patient workspace in read-only mode: already revealed clinical information and
the timeline remain visible, while reveal controls and new orders are disabled.

EXCON can also trigger any pending supported scenario event immediately. The
action asks for confirmation and then uses the normal scenario engine, so the
clinical result, originating order, pending-event list, and timeline remain in
sync without advancing the exercise clock.
